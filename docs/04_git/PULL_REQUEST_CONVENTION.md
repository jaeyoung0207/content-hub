# Pull Request Convention

프로젝트의 PR(Pull Request) 작성 규칙을 정의합니다.  
**이슈 기반 개발 워크플로우**를 따르며, 모든 PR은 이 템플릿을 사용합니다.

---

## 1. 기본 구조

```markdown
## 관련 이슈
Closes #[이슈번호]

## 발생 원인 (이슈 타입이 BUG인 경우)
### 직접 원인 (선택)
- [직접 원인]
### 근본 원인 (선택)
- [근본 원인]

### 해결 방안 (이슈 타입이 BUG인 경우)
- [해결 방안]

## 변경 내용
### 공통   ← 변경 없는 경우 생략
1. [인프라/Git/문서]
- [변경점]

### 백엔드   ← 변경 없는 경우 생략
1. [기능/화면/컴포넌트명]
- [변경점]

### 프론트엔드   ← 변경 없는 경우 생략
1. [기능/화면/컴포넌트명]
- [변경점]

## 테스트 완료 항목
- [ ] 로컬 환경 테스트
- [ ] 기존 기능 영향 없음 확인

## 배포 후 검증 계획 (선택)
[배포 후 확인이 필요한 경우 검증 방법 작성]

## 스크린샷 (선택)
[UI 변경이나 시각적 확인이 필요한 경우 첨부]

## 로그 (선택)
[실행 로그나 테스트 결과 로그가 필요한 경우 첨부, 반드시 코드 블록(백틱)으로 감싸 주세요.]

## 참고사항 (선택)
[추가 설명이나 리뷰어가 알아야 할 내용 작성]
```

## 2. 각 섹션 작성 가이드

### 2.1 관련 이슈

- **필수 항목**
- GitHub Issue와 연결하여 이슈 자동 종료
- 단일 이슈 연결: `Closes #123`
- 복수 이슈 연결: `Closes #123, Closes #456`
- 참조만 하는 경우: `Refs #789`

### 2.2 발생 원인 및 해결 방안

- **BUG 이슈 타입인 경우 필수**
- "직접 원인/근본 원인" 구분 가능하면 각각 작성, 단일 원인만 있으면 하나만 작성
- 원인과 해결방안을 같이 기술(다른 이슈일 때는 생략 가능)

### 2.3 변경 내용

- **필수 항목**
- 커밋 메시지 컨벤션과 동일한 구조 사용
- **항상 공통 → 백엔드 → 프론트엔드 순서**로 작성
- 각 영역 내 **기능/화면/컴포넌트 단위로 번호**를 붙이고, **하위에 리스트**로 변경점 작성
- 공통, 백엔드, 프론트엔드 중 어느 한 쪽만 변경한 경우 **변경 없는 쪽은 생략**
- 변경점이 하나여도 **구조를 반드시 지킴**
- 각 변경점 끝에 `(feat)`, `(fix)`, `(refactor)` 등 작업 성격 명시 가능

### 2.4 테스트 완료 항목

- **필수 항목**
- 기본 체크리스트 2개는 항상 포함
- 추가 테스트 항목이 있으면 추가

```markdown
- [ ] 로컬 환경 테스트
- [ ] 기존 기능 영향 없음 확인
- [ ] E2E 테스트 통과
- [ ] 성능 테스트 완료
```

### 2.5 배포 후 검증 계획

- **선택 항목**
- 운영 환경 배포 후 확인이 필요한 경우 작성
- 구체적인 검증 절차를 단계별로 작성

```markdown
1. 운영 환경 배포 후 EC2 접속
2. `/home/ubuntu/app/logs/` 디렉토리로 이동
3. `ls -l` 명령어로 로그 파일 생성 확인
4. `tail -f [로그 파일명]` 명령어로 실시간 로그 확인
```

### 2.6 스크린샷

- **선택 항목**
- UI 변경, 버그 수정, 시각적 확인이 필요한 경우 첨부
- **Issue에 Before가 있으면 PR에는 After만 첨부해도 됨**
- Before/After 비교가 필요한 경우 명확하게 구분

```markdown
## 스크린샷
### After
![image](https://github.com/user-attachments/assets/...)

## 스크린샷
### Before
![image](https://github.com/user-attachments/assets/...)

### After
![image](https://github.com/user-attachments/assets/...)
```

### 2.7 로그

- **선택 항목**
- CI/CD 실행 로그, 테스트 결과, 에러 로그 등 첨부 시 사용
- **반드시 코드 블록(백틱 3개)으로 감싸서 작성**
- 로그가 길면 핵심 부분만 발췌하거나 접기 기능 사용

**예시 1) 간단한 로그**

```
## 로그
```
Run ./gradlew sonar -Dsonar.token=*** --info
...  
ANALYSIS SUCCESSFUL
BUILD SUCCESSFUL in 40s
```
```

**예시 2) 긴 로그 (접기)**

```
## 로그
<details>
<summary>전체 로그 보기</summary>

```
[전체 로그 내용]
```
</details>
```

### 2.8 참고사항

- **선택 항목**
- 리뷰어가 알아야 할 추가 컨텍스트나 주의사항 작성
- 기술적 배경, 의사결정 이유, 후속 작업 계획 등

```markdown
## 참고사항
- 이 변경은 다음 릴리즈에서 제거될 임시 코드입니다
- 성능 개선을 위해 알고리즘을 O(n²)에서 O(n log n)으로 변경했습니다
- DB 마이그레이션이 필요합니다 (#123 이슈 참고)
```

## 3. 작성 예시

### 예시 1) 공통, 백엔드와 프론트엔드 모두 변경 (버그 수정 포함)

```markdown
## 관련 이슈
Closes #3

## 발생 원인 및 해결 방안
### 직접 원인
- 로그 파일 용량 제한 설정 누락으로 인해 오래된 로그가 무제한 쌓임
### 근본 원인
- 운영 환경 배포 시 application-prod.yml에 관련 설정이 누락됨
### 해결 방안
- 로그 정책 옵션 추가 및 적용 테스트 진행

## 변경 내용
### 공통
1. 인프라
- CI/CD 파이프라인 보안 설정 강화 (feat)
- 프로젝트 문서 내 보안 체크리스트 추가 (docs)

### 백엔드
1. 공통
- application-prod.yml, application-staging.yml 변경 (refactor)
  - 로그 보존 디렉토리 변경
  - 로그 파일 최대 크기, 최대 보관 기간, 전체 용량 제한 설정

### 프론트엔드
1. 인프라
- docker-compose volume 설정으로 컨테이너 로그를 호스트에 보존 (feat)

## 테스트 완료 항목
- [x] 로컬 환경 테스트
- [x] 기존 기능 영향 없음 확인

## 배포 후 검증 계획
1. 운영 환경에 배포 완료 후, EC2 인스턴스에 접속
2. `/home/ubuntu/app/logs/` 디렉토리로 이동
3. `ls -l` 명령어로 로그 파일 생성 확인
4. `tail -f [로그 파일명]` 명령어로 실시간 로그 확인

## 스크린샷
![image](https://github.com/user-attachments/assets/...)
```

### 예시 2) 프론트엔드만 변경 (버그가 아닌 경우 발생 원인/해결 방안 없음)

```markdown
## 관련 이슈
Closes #1

## 변경 내용
### 프론트엔드
1. 공통
- vite.config.ts에서 manualChunks 삭제 (fix)
- index.html 불필요한 주석 삭제 (refactor)

## 테스트 완료 항목
- [x] 로컬 환경 테스트
- [x] 기존 기능 영향 없음 확인

## 스크린샷
![image](https://github.com/user-attachments/assets/...)

## 참고사항
- manualChunks 설정이 정확하지 않은 경로 패턴 때문에 일부 모듈이 잘려나가면서 번들이 깨진 것이 원인
```

### 예시 3) 백엔드만 변경 + 로그 첨부

```markdown
## 관련 이슈
Closes #4

## 변경 내용
### 백엔드
1. 공통
- SonarCloud 가이드라인에 맞게 backend-ci. yml 수정 (fix)
  - SonarQube 패키지 캐시 추가
  - Gradle 캐시 경로 개선
  - SonarQube 분석 처리 수정
  - fetch-depth 설정 추가
  - workflow_dispatch 추가하여 수동 실행 가능하도록 변경
- build.gradle에 SonarQube 플러그인 및 properties 설정 추가 (feat)

## 테스트 완료 항목
- [x] 로컬 환경 테스트
- [x] 기존 기능 영향 없음 확인

## 로그
```
Run ./gradlew sonar -Dsonar.token=*** --info
... 
ANALYSIS SUCCESSFUL, you can find the results at: https://sonarcloud.io/dashboard?id=...
BUILD SUCCESSFUL in 40s
2 actionable tasks: 2 executed
```
```

## 4. 작성 규칙

### 필수 사항
- **관련 이슈**, **변경 내용**, **테스트 완료 항목**은 반드시 작성
- **BUG 이슈(PR)인 경우 '발생 원인 및 해결방안'은 반드시 작성**
- 변경 내용은 커밋 메시지 컨벤션과 동일한 구조 사용
- 공통 → 백엔드 → 프론트엔드 순서 준수
- 변경 없는 쪽은 생략
- 로그 첨부 시 반드시 코드 블록(백틱 3개)으로 감싸기

### 권장 사항
- 제목은 커밋 메시지 컨벤션의 타입과 요약 형식 사용
- 이슈 번호와 브랜치명이 일치하는지 확인
- 테스트는 반드시 완료 후 체크
- 복잡한 변경사항은 배포 후 검증 계획 작성
- UI 변경은 스크린샷 첨부 (Issue에 Before가 있으면 After만 첨부 가능)
- CI/CD 관련 변경은 로그 첨부 권장
- 기술적 배경이나 주의사항이 있으면 참고사항 작성

### 금지 사항
- 이슈 없이 PR 작성 금지
- 필수 항목 생략 금지
- 테스트 미완료 상태로 체크 금지

## 5. PR 제목 규칙

- 커밋 메시지 컨벤션의 타입과 요약 형식 사용
- 형식: `[type]: 주요 변경 요약`

### 예시

```
feat: EC2 운영 환경에서 백엔드/프론트엔드 로그를 호스트 디렉토리에 보존
fix: 어플리케이션 접속 시 화면이 빈 화면으로 표시되는 문제 수정
fix: GitHub Actions backend-ci에서 SonarQube 실행 에러 수정
refactor: API 응답 구조 개선
docs: README 업데이트
```

## 6. PR 작성 프로세스

```
1. 이슈 확인 (#번호)
   ↓
2. 브랜치 생성 (prefix-번호/description)
   ↓
3. 작업 완료 & 커밋
   ↓
4. PR 작성 (이 템플릿 사용)
   ↓
5. 자가 리뷰 & 체크리스트 확인
   ↓
6. 리뷰어 지정 & 제출
   ↓
7. 코드 리뷰 & 피드백 반영
   ↓
8. 승인 후 머지
```

---

## 7. 체크리스트

PR 작성 전 확인:

- [ ] 관련 이슈가 연결되어 있는가?
- [ ] 버그 이슈(PR) 수정 시 발생 원인과 해결방안을 작성했는가?
- [ ] PR 제목이 커밋 컨벤션을 따르는가?
- [ ] 변경 내용이 구조에 맞게 작성되었는가?
- [ ] 테스트를 완료하고 체크했는가?
- [ ] UI 변경 시 스크린샷을 첨부했는가?
- [ ] 로그 첨부 시 코드 블록으로 감쌌는가?

---

이 규칙을 준수하여 PR을 작성해 주세요.

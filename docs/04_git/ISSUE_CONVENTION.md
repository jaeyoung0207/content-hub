# Issue Convention

프로젝트의 GitHub Issue 작성 규칙을 정의합니다.  

---

## 1. Issue 템플릿 종류

프로젝트에서 사용하는 Issue 템플릿은 다음과 같습니다:

1. **Bug Report** - 버그 제보
2. **Feature Request** - 새로운 기능 제안
3. **Refactor** - 리팩터링 작업

---

## 2. Bug Report

버그를 발견했을 때 사용합니다.

### 템플릿

```markdown
## 문제 설명
<!-- 어떤 버그인지 명확하게 설명 -->

## 재현 방법
1. 
2. 
3. 

## 예상 동작
<!-- 어떻게 동작해야 하는지 -->

## 실제 동작
<!-- 실제로 어떻게 동작하는지 -->

## 스크린샷 (선택)


## 로그 (선택)
```

```

## 💻 환경 정보
- OS / 브라우저: 

## 참고사항(선택)
<!-- 추가로 고려해야 할 사항이 있다면 작성
     로그, 에러 등 코드/콘솔 출력은 백틱 3개(```)로 감쌀 것 -->
```

### 작성 예시

```markdown
## 문제 설명
- 어플리케이션 접속 시 화면이 빈 화면으로 표시됨

## 재현 방법
1. https://content-hub.info 접속

## 예상 동작
- 헤더와 홈 화면 표시

## 실제 동작
- 화면이 표시되지 않음

## 스크린샷/로그(선택)
- 스크린샷

![스크린샷](https://github.com/user-attachments/assets/...)
- 로그 (백틱 3개로 감싸기)
```
TypeError: Cannot read property 'foo' of undefined
    at HomePage ...
```

## 💻 환경 정보
- OS / 브라우저: Windows 11 / Edge 버전 142.0.3595.94
```

## 3. Feature Request

새로운 기능을 제안할 때 사용합니다.

### 템플릿

```markdown
## 기능 설명
<!-- 어떤 기능을 추가하고 싶은지 명확하게 설명 -->

## 목적
<!-- 이 기능이 왜 필요한지, 무엇을 개선하려 하는지 -->

## 작업 범위
- [ ] 백엔드
- [ ] 프론트엔드
- [ ] 문서
- [ ] 인프라

## 참고사항(선택)
<!-- 추가로 고려해야 할 사항이 있다면 작성
     로그, 에러 등 코드/콘솔 출력은 백틱 3개(```)로 감쌀 것 -->
```

### 작성 예시

```markdown
## 기능 설명
- 검색 필터에 복수 선택 기능 추가
- 사용자가 여러 미디어 타입을 동시에 선택할 수 있도록 체크박스 UI 제공

## 목적
- 사용자가 한 번에 여러 조건으로 검색할 수 있어 편의성 향상
- 단일 선택만 가능한 현재 UI의 불편함 해소

## 작업 범위
- [ ] 백엔드 - 복수 선택 API 파라미터 지원
- [x] 프론트엔드 - 체크박스 UI 컴포넌트 개발
- [ ] 문서 - API 명세 업데이트
- [ ] 인프라 - 배포 시간 단축

## 참고사항(선택)
- 기존 라디오 버튼 모드와 체크박스 모드를 토글로 전환 가능하게 구현
- 예시 로그:
```
GET /api/v1/media?type[]=ani&type[]=drama
=> 200 OK
```
```

## 4. Refactor

코드 개선/리팩터링 작업을 계획할 때 사용합니다.

### 템플릿

```markdown
## 리팩터링 대상
<!-- 어떤 코드/모듈을 개선할 것인지 -->

## 현재 문제점
<!-- 왜 리팩터링이 필요한지 -->

## 개선 방향
<!-- 어떻게 개선할 것인지 -->

## 작업 범위
- [ ] 백엔드
- [ ] 프론트엔드

## 참고사항(선택)
<!-- 추가로 고려해야 할 사항이 있다면 작성
     로그, 에러 등 코드/콘솔 출력은 백틱 3개(```)로 감쌀 것 -->
```

### 작성 예시

```markdown
## 리팩터링 대상
- API 응답 구조 개선
- 중복된 에러 핸들링 로직 통합

## 현재 문제점
- 각 컨트롤러마다 중복된 예외 처리 코드 존재
- 일관되지 않은 API 응답 형식으로 프론트엔드에서 분기 처리 필요

## 개선 방향
- GlobalExceptionHandler로 통합
- 공통 ResponseDto 클래스 작성하여 모든 API 응답 형식 통일

## 작업 범위
- [x] 백엔드 - GlobalExceptionHandler, ResponseDto 작성
- [ ] 프론트엔드 - 통일된 응답 형식에 맞춰 API 호출 로직 수정

## 참고사항(선택)
- 기존 API 응답 형식을 변경하므로 프론트엔드와 동시 배포 필요
- 테스트 결과 로그:
```
에러 응답 정상 동작 확인 (통합 예외 처리 적용 후)
```
```

## 5. Issue 작성 규칙

### 제목(Title) 규칙

```
[타입] 간결한 요약

예시:
[BUG] 어플리케이션 접속 시 화면이 빈 화면으로 표시됨
[FEAT] 검색 필터 복수 선택 기능 추가
[REFACTOR] API 응답 구조 개선
```

**타입:**
- `[BUG]` - 버그 제보
- `[FEAT]` - 새로운 기능
- `[REFACTOR]` - 리팩터링
- `[DOCS]` - 문서 작업
- `[PERF]` - 성능 개선
- `[TEST]` - 테스트 추가/수정

## 6. Label 규칙

Issue 생성 시 적절한 Label을 추가합니다:

| Label            | 설명              | 사용 예시          |
|------------------|------------------|--------------------|
| **bug**          | 버그 수정         | Bug Report         |
| **enhancement**  | 기능 추가/개선    | Feature Request    |
| **refactor**     | 리팩터링          | Refactor           |
| **documentation**| 문서 작업         | README 수정        |
| **performance**  | 성능 개선         | 쿼리 최적화         |
| **backend**      | 백엔드 작업       | 백엔드 관련         |
| **frontend**     | 프론트엔드 작업   | 프론트엔드 관련      |
| **priority:high**| 긴급/중요         | 치명적 버그         |
| **priority:low** | 낮은 우선순위     | 부가 기능           |

---

## 7. Assignee 규칙

- Issue 생성 시 **담당자를 지정**합니다.
- 1인 개발인 경우 본인을 Assignee로 지정
- 협업 시 작업 담당자를 명확히 지정

---

## 8. 작업 흐름

```
1. Issue 작성
   - 적절한 템플릿 선택
   - 제목에 [타입] 표시
   - Label 추가
   - Assignee 지정
   ↓
2. 브랜치 생성
   - <prefix>-<issue-number>/<description>
   ↓
3. 작업 진행
   ↓
4. PR 생성
   - PR 설명에 "Closes #이슈번호" 작성
   ↓
5. 리뷰 및 머지
   - PR 머지 시 Issue 자동 닫힘
```

---

## 9. 체크리스트

새 Issue 작성 시 확인:

- [ ] 적절한 템플릿을 사용했는가?
- [ ] 제목에 [타입]이 포함되어 있는가?
- [ ] 필수 항목을 모두 작성했는가?
- [ ] Label이 적절하게 추가되었는가?
- [ ] Assignee가 지정되었는가?
- [ ] 스크린샷/로그가 필요한 경우 첨부했는가?

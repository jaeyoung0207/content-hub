# Commit Message Convention

프로젝트의 커밋 메시지 작성 규칙을 아래와 같이 정의합니다.  
이 규칙을 모든 커밋(또는 PR 설명)에 **일관되게 적용**합니다.

---

## 1. 기본 구조

- **타입**: 커밋의 성격을 한 단어로 명시 (feat, fix, refactor, style, docs 등)
- **한 줄 요약**: 변경의 주요 목적을 간결하게 서술

```
[type]: 주요 변경 요약
```

- **상세 변경점**:  
  - 백엔드 변경사항을 먼저, 프론트엔드 변경사항을 그 다음에 작성  
  - 각 영역 내에서는 기능/화면/컴포넌트 단위로 번호를 붙이고, 하위에 리스트로 상세 변경점을 작성  
  - **백엔드 또는 프론트엔드 중 어느 한 쪽만 변경한 경우, 변경 없는 쪽은 생략**한다.

```
백엔드:
1. [기능/화면/컴포넌트명]
- [변경점1]
- [변경점2]

프론트엔드:
1. [기능/화면/컴포넌트명]
- [변경점1]
- [변경점2]
```

---

## 2. 타입(Type) 정의

- **feat**: 새로운 기능 추가, 기존 기능 개선
- **fix**: 버그 수정
- **refactor**: 리팩터링(기능 변화 없는 코드 개선)
- **style**: UI/스타일 변경
- **docs**: 문서 관련 변경
- **test**: 테스트 코드 관련

---

## 3. 기능별 번호/제목/리스트 작성 예시

변경점이 많거나 적어도 항상 아래 구조를 유지합니다.

### 예시 1) 백엔드와 프론트엔드 모두 변경

```
feat: 검색 필터 UI/UX 개선 및 체크박스 컴포넌트 리팩터링

백엔드:
1. 공통
- application.yml 주석 추가(refactor)
2. 검색
- 검색 API 응답 구조 개선

프론트엔드:
1. 헤더
- 검색 필터에 "복수 선택(체크박스)"/"단일 선택(라디오)" 모드 선택 UI 추가(feat)
2. 검색
- 미디어 타입 미선택/데이터 없음 시 "결과 없음" 메시지 표시(feat)
3. 체크박스UI
- label i18n 처리 방식 변경(refactor)
- 라벨 텍스트 크기 Xl→lg로 변경(style)
```

### 예시 2) 프론트엔드만 변경 (백엔드 생략)

```
fix: 검색 화면 placeholder 텍스트 변경

프론트엔드:
1. 검색
- 검색창 placeholder 텍스트 변경
```

### 예시 3) 백엔드만 변경 (프론트엔드 생략)

```
refactor: application.yml 주석 추가

백엔드:
1. 공통
- application.yml 주석 추가
```

---

## 4. 작성 규칙

- 항상 **백엔드 → 프론트엔드** 순서로 작성
- 각 영역 내 **기능/화면/컴포넌트 단위로 번호**를 붙이고, **하위에 리스트**로 변경점 작성
- 각 변경점 끝에 `(feat)`, `(fix)`, `(refactor)` 등 **작업 성격을 명시** (필요시)
- 변경점이 하나여도 **구조를 반드시 지킴**
- 백엔드 또는 프론트엔드 중 어느 한 쪽만 변경한 경우, **변경 없는 쪽은 생략**
- 불필요하게 상세한 코드 설명은 생략, **변경의 목적/핵심만 기술**

---

## 5. 기타

- 커밋 메시지와 PR 메시지 모두 이 규칙을 적용합니다.
- 규칙 예외 없이 항상 동일한 구조로 작성합니다.
- 릴리즈 노트, 자동화 도구, 변경 이력 관리에 활용할 수 있습니다.

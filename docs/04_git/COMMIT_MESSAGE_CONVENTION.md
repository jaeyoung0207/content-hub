# Commit Message Convention

프로젝트의 커밋 메시지 작성 규칙을 아래와 같이 정의합니다.  
이 규칙을 모든 커밋(또는 PR 설명)에 **일관되게 적용**합니다.

---

## 1. 기본 구조

- **타입**: 커밋의 성격을 한 단어로 명시 (feat, fix, refactor, style, docs 등)
- **한 줄 요약**: 변경의 주요 목적을 간결하게 서술

```
[type]: 주요 변경 요약
```

- **상세 변경점**:  
  - **공통, 백엔드, 프론트엔드** 순서로 작성  
  - 공통(인프라/CI/CD/환경 등 두 영역 모두에 해당되거나 둘 다 아닌 리소스)에 대한 변경은 “공통”으로 작성  
  - 각 영역 내에서는 기능/화면/컴포넌트 단위로 번호를 붙이고, 하위에 리스트로 상세 변경점을 작성  
  - **공통, 백엔드, 프론트엔드 중 어느 한 쪽만 변경한 경우, 변경 없는 쪽은 생략**한다.

```
공통:
1. 인프라
- [예: docker-compose.yml, nginx.conf, CI/CD, 환경변수, 인증서 등 변경]

백엔드:
1. [기능/화면/컴포넌트명]
- [변경점1]
- [변경점2]

프론트엔드:
1. [기능/화면/컴포넌트명]
- [변경점1]
- [변경점2]
```

---

## 2. 타입(Type) 정의 및 예외 형식

- **feat**: 새로운 기능 추가, 기존 기능의 눈에 띄는 개선
- **fix**: 버그 수정(기능 동작 오류 해결)
- **refactor**: 리팩터링(동작 변화 없이 구조/가독성/유지보수성 개선)
- **perf**: 성능 개선(N+1 제거, 캐싱, 알고리즘 최적화 등)
- **style**: 포맷팅/코드 스타일/UI 스타일 변경(동작 변화 없음)
- **test**: 테스트 추가/수정/커버리지 개선
- **build**: 빌드 시스템/도구/코드 생성/컴파일러/번들러/Gradle 설정
- **ci**: CI/CD 파이프라인/워크플로우 설정(GitHub Actions, Jenkins 등)
- **chore**: 소스/테스트 외 유지보수 작업(스크립트, 폴더 정리, 메타 파일 등)
- **chore(deps)** 또는 **deps**: 의존성 업데이트/정리

### **예외**
- **docs**:  
  - `docs: [제목]` 형태로 한 줄로 작성 → 필요시 한 줄 아래에 세부 변경 사항을 리스트로 추가  
    ```
    docs: API 명세 최신화
    - User API 설명 업데이트
    - 오류 코드 목록 추가
    ```
- **revert**:  
  - `revert: "[되돌리는 커밋 제목]"`  
    (타입만 작성한 후, 되돌리는 대상 커밋 타이틀을 큰따옴표로 감싼다)
    ```
    revert: "ci(backend): 프론트엔드 CI 워크플로우 추가"
    ```
- **기타 타입**(위 예외 외): 타입 + 제목 + 상세 변경점 구조를 반드시 따름

## 3. 기능별 번호/제목/리스트 작성 예시

변경점이 많거나 적어도 항상 아래 구조를 유지합니다.

### 예시 1) 공통/인프라(백엔드/프론트엔드 외 리소스)

```
fix: docker compose 빌드 명령어 수정

공통:
1. 인프라
- docker-compose.yml 빌드 명령어를 'build'에서 'up --build'로 수정
```

### 예시 2) 백엔드와 프론트엔드 모두 변경

```
feat: 검색 필터 UI/UX 개선 및 체크박스 컴포넌트 리팩터링

백엔드:
1. 공통
- application.yml 주석 추가(refactor)
2. 검색
- 검색 API 응답 구조 개선

프론트엔드:
1. 헤더
- 검색 필터에 "복수 선택(체크박스)"/"단일 선택(라디오)" 모드 선택 UI 추가(feat)
2. 검색
- 미디어 타입 미선택/데이터 없음 시 "결과 없음" 메시지 표시(feat)
3. 체크박스UI
- label i18n 처리 방식 변경(refactor)
- 라벨 텍스트 크기 Xl→lg로 변경(style)
```

### 예시 3) 프론트엔드만 변경 (백엔드 생략)

```
fix: 검색 화면 placeholder 텍스트 변경

프론트엔드:
1. 검색
- 검색창 placeholder 텍스트 변경
```

### 예시 4) 백엔드만 변경 (프론트엔드 생략)

```
refactor: application.yml 주석 추가

백엔드:
1. 공통
- application.yml 주석 추가
```

### 예시 5) docs 형식

```
docs: README 업데이트
- 새 설치 가이드 추가
- 버전 뱃지 갱신
```

### 예시 6) revert 형식

```
revert: "fix: 로그인 실패 시 에러 핸들링 방식 수정"
```

## 4. 작성 규칙

- 항상 **공통 → 백엔드 → 프론트엔드** 순서로 작성
- 각 영역 내 **기능/화면/컴포넌트 단위로 번호**를 붙이고, **하위에 리스트**로 변경점 작성
- 각 변경점 끝에 `(feat)`, `(fix)`, `(refactor)` 등 **작업 성격을 명시** (필요시)
- 변경점이 하나여도 **구조를 반드시 지킴**
- 공통, 백엔드 또는 프론트엔드 중 어느 한 쪽만 변경한 경우, **변경 없는 쪽은 생략**
- 불필요하게 상세한 코드 설명은 생략, **변경의 목적/핵심만 기술**
- **메시지 톤**: 명령형 현재형으로 간결하게 작성 (예: “추가”, “수정”, “정리”)
- **스코프(scope)**: 영향 범위를 괄호로 명시하는 것을 권장 (예: `build(frontend)`, `feat(search)`)
- **Breaking change**(이전 버전과 호환되지 않는 변경):
  - 제목 느낌표 또는 바디 푸터에 `BREAKING CHANGE:` 기재
  - 기존 클라이언트/호출자가 반드시 수정해야 하는 변경 시 사용
- **이슈 연계**: 필요 시 바디 푸터에 참조/종료 키워드 사용 (예: `Closes #123`, `Refs #456`)

---

### [영역 구분 안내]

- **공통:**  
  - 두 영역 모두에 해당되거나, 백엔드/프론트엔드 이외의 리소스(인프라, 배포, 환경설정, CI/CD, docker-compose.yml, Nginx 설정, 인증서, .env, AWS 인프라 등)
- **백엔드/프론트엔드:**  
  - 프로젝트 내 각 역할에 해당하는 실제 서비스 코드, 패키지, API, 화면, UI, 컴포넌트 등

---

## 5. 기타

- 커밋 메시지와 PR 메시지 모두 이 규칙을 적용합니다.
- 규칙 예외 없이 항상 동일한 구조로 작성합니다.
- 릴리즈 노트, 자동화 도구, 변경 이력 관리에 활용할 수 있습니다.

---

## 6. 템플릿

```
[type]: 주요 변경 요약

공통:   ← 변경 없는 경우 생략
1. 인프라
- [ex: docker-compose.yml, nginx.conf, CI/CD, 환경변수 등 공통 변경점]

백엔드:   ← 변경 없는 경우 생략
1. [기능/화면/컴포넌트명]
- [변경점]

프론트엔드:   ← 변경 없는 경우 생략
1. [기능/화면/컴포넌트명]
- [변경점]

Footer(선택):
BREAKING CHANGE: [이전 버전과 호환되지 않는 변경 설명]
Closes #123
```

### docs 예외 템플릿

```
docs: [제목]
- 세부 변경점1
- 세부 변경점2
```

### revert 예외 템플릿

```
revert: "[되돌리는 커밋 타이틀]"
```
